# telegram-shared-room-relay

한 텔레그램 방에 사용자와 두 개의 AI 에이전트(봇)가 함께 대화할 수 있게 해 주는 중계 서버입니다. 텔레그램 봇은 다른 봇의 메시지를 볼 수 없기 때문에, 중계 서버가 공용 대화록(transcript)을 보관하고 각 에이전트는 중계를 통해 상대방의 발언을 읽고 답합니다. 어느 한쪽이 같은 내용을 두 번 읽거나 두 번 쓰지 않도록, 읽기 커서와 쓰기 멱등 키를 규약으로 강제합니다.

A relay server that lets a user and two AI agents (bots) share one Telegram room. Telegram bots cannot see each other's messages, so the relay keeps the shared transcript and each agent reads and replies through it. The contract enforces a durable read cursor and write idempotency keys so neither side ever reads or sends the same thing twice.

- Server: Cloudflare Workers + Durable Object (SQLite).
- Client: any language. A verified Python reference client is included.
- Costs: expected $0 on the Cloudflare free plan at room-level traffic; limits change, so check current Cloudflare pricing before relying on this. Telegram bots are free.

## Quickstart (what a new agent needs)

Inputs, by kind. "Only two things" is not accurate; these are all of them:

| Kind | What | Who provides it |
|---|---|---|
| From the user | A Cloudflare account (free plan) and a way to authenticate wrangler: browser login (`npx wrangler login`) or an API token with Workers edit rights | User |
| From the user | A Telegram bot token from @BotFather | User |
| From the user | The shared room (add the bot to it) and which Telegram user ids may speak; the numeric ids are discovered after the bot is in the room (SETUP step 4) | User, then read from the relay |
| Generated by the agent | Three random secrets: one Bearer token per agent plus a webhook path secret (`openssl rand -hex 32`) | Agent |
| Per agent client config | Relay URL, that agent's Bearer token, sender label, and paths for the cursor and outbox files | Agent |
| Runtime prerequisites | Node >= 22 and npm (wrangler, tests), Python >= 3.10 (client and offline checks), `openssl` and `curl` | Machine |
| Optional | Deployed self-test (temporary cron and two vars), see SETUP step 2 | Agent |

Tool versions are pinned (`cloudflare/package.json` for wrangler, `tests/package.json` for miniflare) with lockfiles, so use `npm ci`, not `npx` latest.

```bash
cd cloudflare
npm ci                                   # installs pinned wrangler
cp wrangler.toml.example wrangler.toml
npx wrangler login                       # or export CLOUDFLARE_API_TOKEN
npx wrangler deploy                      # TEST_MODE=1: no real Telegram sends
npx wrangler secret put BOT_TOKEN        # Telegram bot token
npx wrangler secret put INSTINCT_TOKEN   # random Bearer token for agent A
npx wrangler secret put PICKLE_TOKEN     # random Bearer token for agent B
npx wrangler secret put WEBHOOK_SECRET   # random path secret
```

The first deploy on a new account may ask the user to register a workers.dev subdomain. Full steps, self-test, webhook registration, and live cutover: [docs/SETUP.md](docs/SETUP.md).

## Verify before you trust it

```bash
cd tests && npm ci && npm test                            # 49 checks
python3 tools/relay_check.py                                # 18 checks, fully offline
python3 tools/relay_check.py --serve                        # mock server for your own client
```

Current status: the worker passed the 49-check local suite, the 18-check offline harness, and a 24-check self-test on a real test deployment (TEST_MODE). The example client passed independent crash-recovery reproduction (response-loss after server accept, restart, same-key recovery, no duplicate). The relay has **not** been connected to a live Telegram room yet; that is the remaining cutover step in docs/SETUP.md.

## The one rule that matters most

Never resend with a new idempotency key after an ambiguous failure (timeout, 5xx, lost response). Record intent + key to a durable outbox **before** the first send, and re-query with the same key. See `examples/relay_client.py` for a complete implementation and [docs/CONTRACT.md](docs/CONTRACT.md) for why.
